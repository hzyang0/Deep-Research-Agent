# Web 界面架构（Web Architecture）

本文说明可视化界面这一层的设计。核心观点：**界面是"表现层"，它很薄，不含任何研究逻辑** —— 这正是好架构的体现，也是面试时可以展开的点。

## 整体分层

```
浏览器 (单页前端, 零构建 HTML/CSS/JS)
   │  ① POST /api/research  携带问题与参数
   │  ② SSE 流式接收事件，实时渲染
   ▼
FastAPI 后端 (web/server.py)  ← 表现层，薄薄一层
   │  把请求转交给 Agent，订阅其事件，转成 SSE 往外推
   ▼
DeepResearchAgent (deep_research/)  ← 核心，与界面无关
   通过 event_sink 回调发出结构化事件
```

关键：**CLI 和 Web 共用同一个 `DeepResearchAgent`**，没有任何重复实现。差别只在"谁来消费事件"——CLI 直接打印，Web 转成 SSE。

## 三个值得讲的设计决策

### 决策一：用回调（event_sink）解耦核心与界面

`ResearchState` 上有一个可选的 `event_sink` 回调。Agent 在每个关键节点（规划完成、收录发现、子问题结束、报告生成）调用 `state.emit(类型, 数据)`。

- CLI 场景：不注入 sink，`emit` 直接返回，行为和加界面前完全一致。
- Web 场景：注入一个把事件投递到队列的 sink。

> **🎣 钩子**："加了 Web 界面会不会把核心代码搞乱？"
> **✅ 答法**：不会。我用一个可选回调做桥梁，核心 Agent 完全不知道接收方是终端还是浏览器。不注入回调时行为和原来一字不差，原有测试全部照常通过——这是"对扩展开放、对修改封闭"的体现。

### 决策二：SSE 而非 WebSocket

研究过程的数据流是**单向**的：后端不断把进度推给前端，前端在研究中不需要回传。这正是 Server-Sent Events 的设计场景：基于普通 HTTP、实现简单、自动重连。

> **🎣 钩子**："为什么不用 WebSocket？"
> **✅ 答法**：WebSocket 是双向的，功能更强但更重。我这里是纯单向推送，SSE 恰好够用。选择"恰好够用"而非"最酷"的技术，是工程成熟度。如果将来要做"研究中途人工干预"这类双向交互，再升级到 WebSocket 不迟。

### 决策三：同步 Agent + 后台线程 + 队列

`agent.run()` 是同步阻塞的（内部是串行网络请求）。直接在请求处理函数里跑会阻塞事件循环。所以：Agent 丢到后台线程跑，事件投递到线程安全队列，SSE 生成器从队列取事件往外发。一个 `None` 哨兵标记结束。

> **🎣 钩子**："阻塞的 Agent 怎么和异步的 Web 框架配合？"
> **✅ 答法**：后台线程跑阻塞任务，通过线程安全队列把事件桥接给异步的 SSE 生成器。这是"同步阻塞任务 + 异步流式输出"的经典模式。异常也转成 error 事件发出，保证前端不会无限等待。

## 前端为什么零构建（不用 React）

刻意选择纯 HTML/CSS/JS 单文件，不引入 React/构建链。

> **🎣 钩子**："为什么不用 React，是不会吗？"
> **✅ 答法**：是权衡后的选择。React 需要 node 环境、npm install、打包配置，会抬高别人跑起项目的门槛。这个界面的复杂度（一个表单 + 事件驱动的增量渲染）用原生 JS 完全可以优雅实现，零依赖、浏览器直接打开。把简单的事情用简单的方式做，是务实。界面再复杂、要做组件复用时，上 React 才有价值。

## 事件协议

后端推送的结构化事件类型（前端按 type 分发渲染）：

| 事件 | 触发时机 | 前端渲染 |
| --- | --- | --- |
| `phase` | 进入某阶段 | 顶部阶段药丸高亮 |
| `plan` | 规划完成 | 生成子问题卡片 |
| `subq_start` | 开始某子问题 | 卡片点亮为"进行中" |
| `search` | 发起一次检索 | 卡片内显示查询词 |
| `finding` | 收录一条发现 | 卡片内追加发现 + 来源链接 |
| `subq_done` | 子问题结束 | 卡片标记完成 + 原因（充分/达上限） |
| `gaps` | 全局反思发现缺口 | 追加补充子问题卡片 |
| `log` | 任意文本日志 | 右侧轨迹流追加一行 |
| `done` | 研究完成 | 渲染报告 + 来源 + 成本徽章 |

注意 `subq_done` 的 reason 字段直接对应后端 `while...else` 区分的两种退出原因（信息充分 / 达搜索上限）——**界面把后端的防死循环逻辑可视化了出来**，这是个很好的演示点。
