# Web 界面与多轮对话架构（Web & Conversation Architecture）

本文说明可视化界面与**多轮研究对话**这一层的设计。核心升级：从"一次性研究"变成"有状态的多轮研究对话"，用户可以在出报告后继续追问、要求深入某点、补充新角度。

## 整体分层

```
浏览器 (React 聊天界面, CDN 零构建)
   ↕ WebSocket 双向长连接
   - 发: 用户每一轮消息
   - 收: Agent 实时事件(规划/检索/发现/反思) + 助手回复
   ▼
FastAPI 后端 (web/server.py)  ← 表现层,很薄
   - 一条 WebSocket = 一段会话
   - 同步 Agent 丢线程跑, asyncio 队列桥接事件回协程
   ▼
ConversationSession (deep_research/agent/conversation.py)  ← 多轮编排
   - 意图分类 → 路由到不同处理
   - 累积发现(跨轮复用) + SQLite 持久化
   ▼
DeepResearchAgent  ← 单轮研究核心(被会话层复用, 保持无状态简单)
```

## 为什么用 WebSocket 而非 SSE（核心面试谈资）

这是一次**有据可依的技术演进**，最值得讲：

- **早期需求**（单向看结果）：数据只从服务器流向浏览器，SSE 恰好够用，我用了 SSE，没有上 WebSocket——因为单向场景下 WebSocket 是过度设计。
- **现在需求**（多轮对话 + 实时追问/深入指令）：前端要在会话过程中持续向后端发消息，后端也持续推事件——**数据流变成双向**。SSE 只能单向，做双向得拼凑（SSE 收 + 额外 POST 发），既别扭又难管理会话连接。WebSocket 为双向、长连接、有状态会话而生，正好匹配。

> **🎣 钩子**："为什么从 SSE 换成 WebSocket？"
> **✅ 答法**：选型由需求驱动。单向时我用 SSE（够用就好，不过度设计）；需求升级为双向多轮对话后，才换 WebSocket。这个演进过程本身说明我的技术决策是看需求、不是追新。

## 多轮对话的灵魂：意图分类

多轮研究 Agent 最难的不是"能聊"，而是"听懂用户这轮要什么"。同一句"那性能方面呢？"，可能是对上一份报告的追问，也可能是要求深入检索——含义取决于上下文。

我用一个轻量 LLM 调用（FAST 档）把每轮消息分类成四种意图，路由到不同处理：

| 意图 | 含义 | 处理 | 成本 |
| --- | --- | --- | --- |
| NEW_RESEARCH | 全新主题 | 跑完整规划-执行-反思 | 高 |
| DEEPEN | 深入某方面 | 派生新子问题，定向补充检索 | 中 |
| REFINE | 补充新角度 | 派生新子问题，检索 | 中 |
| FOLLOW_UP | 基于已有发现可答 | **不检索**，直接用累积发现回答 | 低 |

> **🎣 钩子**："多轮对话，你每轮都重新跑一遍完整研究吗？"
> **✅ 答法**：不会，那样又慢又贵还浪费上下文。我做了意图分类：追问类（FOLLOW_UP）直接用已积累的发现回答，根本不重新检索；只有要深入或换角度时才触发定向检索。这样既省成本，又真正利用了多轮对话累积的上下文。这是有状态 Agent 区别于无状态问答的关键。
>
> **🎣 进阶钩子**："意图分类用什么模型？"
> **✅ 答法**：FAST 档小模型——短文本分类是简单任务，又是每轮都调的高频操作，正好是模型分级该省钱的地方。而且没有历史研究时我用规则直接短路成 NEW_RESEARCH，省掉这次调用。

## 跨轮状态：发现累积 + SQLite 持久化

`ConversationSession` 累积所有轮次产生的发现（`findings`）。这是"多轮"的价值所在——第二轮的追问能用第一轮的发现回答，深入轮的新发现也并入同一个池子。

会话通过 SQLite 持久化（单文件、零配置、Python 内置），断线重连可恢复，也为多用户/多会话留好扩展空间。

> **🎣 钩子**："为什么单独做一个会话层，不把多轮逻辑塞进 Agent？"
> **✅ 答法**：关注点分离。DeepResearchAgent 的职责是"把一个问题研究透"（单轮、无状态、可被 CLI 直接复用）；多轮的状态管理、意图路由、历史维护是另一组关注点，放在 Session 层。Session 是"编排 Agent 的更上层编排器"。这样两层都简单、可独立测试。

## 并发模型：同步 Agent + 线程 + asyncio 队列

`agent.run()` 是同步阻塞的。WebSocket 处理协程里不能直接跑它（阻塞事件循环）。所以用 `asyncio.to_thread` 把整轮处理丢到线程池；Agent 在线程里产生的事件，通过 `loop.call_soon_threadsafe` 安全投递到 asyncio 队列；协程从队列取出再 `await ws.send_json`。

> **🎣 钩子**："阻塞的 Agent 怎么和异步的 WebSocket 配合？"
> **✅ 答法**：后台线程跑阻塞任务，通过线程安全的方式把事件桥接到 asyncio 队列，协程消费队列往 WebSocket 推。这是"同步阻塞任务 + 异步双向通道"的标准桥接。

## 前端为什么 React + CDN 零构建

用 React 做组件化（消息气泡、工作面板都是组件，状态驱动增量更新），但通过 CDN 引入 React/Babel/Tailwind，浏览器内编译，**不需要 node 构建链**。

> **🎣 钩子**："为什么不用 Vite/webpack 正经构建？"
> **✅ 答法**：这是面试演示与开箱即用场景的权衡。CDN 零构建让任何人 clone 下来浏览器直接打开，不用 npm install。代价是生产环境少了打包优化——真要上生产我会换成正经构建链。当前阶段，降低别人跑起来的门槛比构建优化更重要。

## 一个诚实的局限：没做"可中断"

当前是**追问式**多轮（一轮研究跑完再交互），没做"研究进行中实时打断"（interruptible）。

> **🎣 钩子**："研究跑到一半能打断吗？"
> **✅ 答法**：目前不能，这是我**有意识的取舍**。可中断要处理正在跑的循环如何安全响应中断信号、状态一致性等问题，复杂度高、容易出隐蔽 bug。我评估后选择先做扎实的追问式多轮——它已经覆盖了绝大多数"持续深入"的需求，且能清晰展示意图分类、状态复用这些有状态 Agent 的核心。可中断是明确的下一步演进方向。

## 事件协议

| 事件 | 时机 | 前端渲染 |
| --- | --- | --- |
| `session` | 会话建立 | 记录 session_id（用于持久化恢复） |
| `intent` | 意图分类完成 | 助手气泡上的意图标签 |
| `phase` | 进入某阶段 | 工作面板阶段高亮 |
| `plan` | 规划/派生子问题 | 工作面板生成子问题卡片 |
| `subq_start`/`search`/`finding`/`subq_done` | 检索内循环各步 | 卡片实时更新 |
| `turn_done` | 本轮结束 | 渲染回答/报告 + 来源 |
| `error` | 出错 | 错误气泡 |
